  ---
  效能檢查這裡有個張力
  
  你說「需檢查 SQL 語法與效能，避免 DB 瓶頸」，但這兩件事的複雜度差很多：

  語法檢查                         效能檢查
  ──────────────────────────       ──────────────────────────────
  可以用 sqlfluff 或               需要對 Oracle 執行 EXPLAIN PLAN
  sql-parse 在 sidecar             → 要連 DB
  純 parsing，不碰 DB              → 結果因資料量、index 而異
  快、可即時顯示                    → 慢、且結果要人工判讀

  效能檢查的實際做法選項：

  ┌───────────────────────────────┬─────────────┬───────────────────────────────────────────────────┐
  │             方式              │    優點     │                       缺點                        │
  ├───────────────────────────────┼─────────────┼───────────────────────────────────────────────────┤
  │ EXPLAIN PLAN（連 DB）         │ 最準確      │ 要額外一次 DB 連線；使用者需懂執行計劃            │
  ├───────────────────────────────┼─────────────┼───────────────────────────────────────────────────┤
  │ 簡單 heuristic（client-side） │ 快、不連 DB │ 不精確，只能抓明顯問題（如 SELECT *、沒有 WHERE） │
  ├───────────────────────────────┼─────────────┼───────────────────────────────────────────────────┤
  │ 設定 row limit / timeout 護欄 │ 最簡單實作  │ 不是「事前」檢查，而是「出問題時」截止            │
  └───────────────────────────────┴─────────────┴───────────────────────────────────────────────────┘

  你心目中的「效能檢查」比較接近哪種？純粹的護欄（加 ROWNUM 上限）還是真正的 EXPLAIN？

  這個 feature 和現有設計的一個衝突

  design.md 目前的安全策略是：

  ▎ SQL injection 風險 → 所有查詢使用 Oracle named parameters，不做字串拼接

  ---
  1. Test DB 的資料量 caveat
  
  Test DB 試跑通過 ≠ 正式 DB 一定快。如果 test DB 的資料量遠小於正式 DB，這個「效能檢查」給的是假安全感。

  Test DB:  cpnt_execution_log 有 1 萬筆
  Prod DB:  cpnt_execution_log 有 1000 萬筆

  → Test 跑 0.2s 過了，Prod 跑 30s 還在轉

  幾個應對方式：

  ┌──────────────────────────────┬───────────────────────────────────────────┬──────────────────────────────┐
  │             方式             │                   作法                    │             效果             │
  ├──────────────────────────────┼───────────────────────────────────────────┼──────────────────────────────┤
  │ 接受現狀                     │ Test 試跑只是基本過濾                     │ 簡單，但有漏網之魚           │
  ├──────────────────────────────┼───────────────────────────────────────────┼──────────────────────────────┤
  │ 加 prod-side timeout         │ 正式跑也設 timeout，超時回 partial result │ 最實用的護欄                 │
  ├──────────────────────────────┼───────────────────────────────────────────┼──────────────────────────────┤
  │ 強制 ROWNUM/FETCH FIRST 上限 │ 後端自動 wrap SQL 加 row limit            │ 防止大量資料撈出，但改了 SQL │
  └──────────────────────────────┴───────────────────────────────────────────┴──────────────────────────────┘

  你們的 test DB 資料量與 prod 差距大嗎？ 這決定 test 試跑的可信度。

  2. 有些 Fab 失敗、有些成功，要怎麼顯示？

  ---
  3. 合併後的分頁策略

  這個比較技術性，但影響 UX：

  選了 14 個 Fab，每個回 500 rows → 合併後 7000 rows

  要全撈回來再分頁，還是讓每個 Fab 各自帶 ROWNUM 限制？

  方案 A: 後端全撈，前端分頁（client-side pagination）
    + 簡單實作
    - 大量資料傳輸

  方案 B: SQL 強制加 FETCH FIRST N ROWS ONLY
    + 控制資料量
    - 每個 Fab N rows，合併後最多 14×N rows，語意上有點奇怪

  方案 C: 先抓第一頁，使用者翻頁再去 DB 撈
    + 最標準的做法
    - 實作最複雜（要傳 cursor / offset）

  考量到這是 internal tool，方案 A 或 B 應該夠用，不需要 cursor-based pagination。你們預期一次查詢大概多少 rows 是合理的上限？

  串流顯示架構

  你說「一個廠區回傳後即顯示」，這需要後端非同步 + 前端增量更新。架構選項：

  方案 A: SSE（Server-Sent Events）        ← 推薦
  ────────────────────────────────────────────────────────
    前端                後端 (Go)           各 Fab sidecar
    ──────              ──────              ───────────────
    POST /sql/execute
    → 拿到 execution_id
    GET /sql/stream/{id}  ←── 開 SSE 連線
                          ├── goroutine F12A ──► sidecar F12A
                          ├── goroutine F14A ──► sidecar F14A
                          └── goroutine SOIC ──► sidecar SOIC

    F12A 完成 ──────────► event: fab_result {fab:"F12A", rows:[...]}
    SOIC 完成 ──────────► event: fab_result {fab:"SOIC", rows:[...]}
    F14A 超時 ──────────► event: fab_error  {fab:"F14A", error:"timeout"}
                          event: complete

  方案 B: Polling
  ────────────────
    前端每 1s 輪詢 GET /sql/status/{id}
    → 比較簡單，但有 1s 延遲感，且 Angular 要管 interval

  方案 C: WebSocket
  ────────────────
    雙向通訊，這個場景用不到雙向，over-engineering

  SSE 在 Angular 的實作很直覺：

  // RxJS + EventSource
  this.eventSource = new EventSource(`/api/sql/stream/${executionId}`);
  fromEvent(this.eventSource, 'fab_result')
    .pipe(map(e => JSON.parse(e.data)))

  - 情境三（純查詢）→ 沒有 diff，只看 flat table
  - 情境一（設定稽核）→ Diff Panel 直接告知差異在哪，高亮 cell 確認
  - 情境二（數值比較）→ Pivot 橫向比較最直覺

  ---
  Diff 的計算邏輯
  
  「哪些 cell 需要高亮」這個演算法其實有些細節：

  對於每個 column：
    取所有 fab 的值 → SET

    如果 |SET| == 1：所有廠一致 → 不高亮
    如果 |SET| > 1：有差異 → 高亮差異值

  但有些欄位本來就「應該不同」：
    api_url 裡面包含廠區代號 (http://f12a.com/...) → 差異是預期的
    這個要怎麼處理？

  有兩個方向：
  - 讓使用者標記「預期差異欄位」：可在 context SQL config 裡加 ignore_diff_columns: [api_url]
  - 不處理，使用者自己判斷：保持簡單，diff 只是提示，不是規則

  你覺得前者值得做嗎？還是先保持簡單？
